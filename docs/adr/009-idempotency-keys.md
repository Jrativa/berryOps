# ADR-009: Idempotency keys stored inside the business transaction

- Status: Accepted
- Implementation status: not implemented (no `idempotency_keys` table, no `Idempotency-Key` handling). Planned in
  task T2.3 with the stock ledger.

## Context

Mobile users double-tap "Despachar", networks retry, and a dispatch deducts stock. Running a command twice must
end in the same state as running it once, even after a crash halfway.

## Decision

- Command `POST`s (dispatch, reserve, payments, stock movements, ...) require an `Idempotency-Key` header,
  generated by the client once per opened form.
- The key row `(organization_id, key, user_id, endpoint, request_hash, response)` is inserted **in the same
  transaction** as the command (ADR-003) with `ON CONFLICT DO NOTHING`:
  - same key and same request hash: replay the stored response;
  - same key, different hash: 422 `IDEMPOTENCY_KEY_REUSED`;
  - concurrent duplicate: blocks on the unique index, then replays;
  - failed or rolled-back attempt: leaves no key, so a retry runs normally.
- State guards under the aggregate's row lock and the ledger's unique source key are a second barrier
  (two devices dispatching the same sale: 409 `INVALID_STATE_TRANSITION`).

## Alternatives considered

- **Key store in Redis or a separate transaction.** Pros: fast, independent. Cons: key and effect can disagree after
  a crash (key saved, effect lost, or the reverse). Rejected: one transaction removes that window.
- **Rely on state guards only.** Pros: no extra table. Cons: operations without a natural state change (payments)
  could duplicate. Kept as defense, not sole mechanism.
- **Client-side disabling of buttons.** Helps UX but proves nothing to the server.

## Consequences

- Stored responses grow; cleanup of old keys is deferred (see [../tech-debt.md](../tech-debt.md)).
- Every protected endpoint needs a stable request hash (canonical body).
- The frontend must send a fresh key per form instance, not per click.
